# 03. アーキテクチャ設計（初版）

最終更新: 2026-09-06（計画ラウンド4完了時点）

この文書は「何を、どこで、どう繋ぐか」を定める。個別ソフトの版や設定値は、
構築フェーズの手順書（`docs/1x-*.md` 予定）に分離する。

## 1. 全体像

```
┌──────────────────────────── 自宅 ────────────────────────────┐
│                                                               │
│  Mac Studio（macOS / サーバー＋LLM 専用 / 鍵なし）              │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ Tor デーモン（全外部通信の出口。onion サービスの入口） │    │
│  ├──────────────┬───────────────┬───────────────────────┤    │
│  │ Bitcoin Core │ Fulcrum       │ LLM 推論サーバー       │    │
│  │ (onion-only) │ (Electrum SV) │ (Metal / MLX)          │    │
│  ├──────────────┴───────────────┼───────────────────────┤    │
│  │ ダッシュボード（自ノード集計） │ LLM Web UI（RAG 含む） │    │
│  └──────────────────────────────┴───────────────────────┘    │
│        ▲ onion (client auth)          ▲ onion (client auth)   │
└────────┼──────────────────────────────┼───────────────────────┘
         │ Tor                          │ Tor
   ┌─────┴─────┐                  ┌─────┴─────┐
   │ Tails PC  │                  │ Android   │
   │ Electrum  │                  │ Orbot /   │
   │ 署名・送金 │                  │ Tor Browser│
   └───────────┘                  └───────────┘
```

原則:

1. **鍵は Mac Studio に存在しない**（ADR-002）。署名は Tails。
2. **外に出る通信は Tor だけ**（ADR-003）。内に入る通信は onion サービスだけ（ADR-009）。
3. **本機で人間が触るのは管理画面だけ**（ADR-008）。

## 2. コンポーネント一覧

|---|---|---|---|---|

| C3 | Electrum サーバー | **Fulcrum**（代替: electrs） | macOS ネイティブ | 第一候補 |
| C4 | LLM 推論 | **LM Studio**（代替: Ollama、llama.cpp 直接） | macOS ネイティブ（GPU 必須） | 第一候補 |
| C5 | LLM Web UI / RAG | **Open WebUI**（代替: LM Studio 内蔵 UI のみ） | コンテナ（OrbStack）または Python | 第一候補 |

### 2.1 各候補の選定理由

- **C2 Bitcoin Core**: 唯一の完全検証ノード実装。`onlynet=onion` で Tor 限定にできる。
  8TB あるので prune せず全履歴保持、`txindex=1` で Fulcrum とダッシュボードの要件を満たす。
- **C3 Fulcrum**: electrs より索引構築が速く、macOS 向けビルドが公式配布されている。
  Electrum（Tails）と Electrum Android の両方から onion 経由で接続できる。
  初回索引構築は数時間から半日程度（M3 Ultra なら短い側）。
- **C4 LM Studio**: GUI で完結し、Apple Silicon 向け MLX バックエンドに対応。
  OpenAI 互換 API を出せるので C5 から叩ける。コピペ基準（ADR-007）に最も適合する。
  Docker はホストの GPU を使えないため、推論だけは必ずネイティブで動かす。
- **C5 Open WebUI**: ブラウザから使えるチャット UI。文書アップロードによる RAG、
  会話履歴、複数モデル切替を備える。onion 化して Tails と Android から同じ UI を使う。
- **C6 mempool**: 自ノードのデータだけで手数料・ブロック・トランザクションを可視化できる。
  ただし構成が重い（DB ＋ バックエンド ＋ フロント）ので、必要性を見て採否を決める。

## 3. メモリ・ストレージ配分（設計値）

| 用途 | メモリ | ストレージ | 備考 |
|---|---|---|---|
| macOS ＋ 常駐 | 〜16GB | 〜200GB | |
| Bitcoin Core | 〜32GB（dbcache を大きく取る） | 〜1TB（全履歴、今後の増加分含む） | 初回同期を高速化 |
| Fulcrum | 〜16GB | 〜200GB | 索引 |
| LLM 推論 | **〜400GB** | モデル置き場 〜2TB | 512GB の主用途。最大級のモデルを 1 本載せられる |
| Open WebUI ＋ RAG | 〜8GB | 〜100GB | 文書のベクトル索引 |
| ダッシュボード | 〜8GB | 〜100GB | |
| 予備 | 残り | 残り 〜4TB | |

LLM 推論に約 400GB を割り当てる前提で、他サービスの合計を 100GB 以内に収める。
Bitcoin Core の dbcache は初回同期中だけ大きく取り、同期後は縮小する。

## 4. LLM モデル方針

用途（日本語壁打ち、文書・翻訳・要約、RAG、コマンド作成支援）に対して、
**「日本語に強い最大級の汎用モデル」1 本 ＋ 「軽量で速いモデル」1 本** の 2 段構成にする。

- 大型: 品質優先。長文の要約や難しい相談に使う。応答は遅くてよい
- 小型: 速度優先。日常の短い質問、RAG の下処理、コマンド生成に使う

具体的なモデル名と量子化は、構築時点で公開されている最新の候補から選ぶ（この文書には固定しない）。
選定基準:

1. 日本語の生成品質（ベンチマークより、実際に日本語で数問試す）
2. 512GB に収まる量子化で、実用的な速度（体感で人が読む速さ以上）が出ること
3. ライセンスが個人利用に問題ないこと

モデルの取得経路（Tor 経由に限定するか）は未決（ラウンド5）。

## 5. ネットワーク設計

### 5.1 送信（本機 → 外）

- macOS のシステム全体を強制 Tor 化することはしない（macOS では不完全になりやすい）。
  代わりに、**外に出る必要のあるプロセスを列挙し、それぞれを Tor の SOCKS に向ける**。
  - Bitcoin Core: `proxy=127.0.0.1:9050`, `onlynet=onion`, `listen=1`, `bind=127.0.0.1`
  - Homebrew / curl / git: 環境変数で SOCKS プロキシを指定
  - LM Studio / モデル取得: 未決（ラウンド5）
  - ダッシュボードの外部データ取得: 未決（ラウンド5）
- macOS の自動更新やテレメトリは、必要最小限に絞る設定を手順化する

### 5.2 受信（外 → 本機）

- ルーターのポート開放なし。LAN 内でもサービスを平文で listen させない（127.0.0.1 のみ）
- Tor の onion サービス（v3、クライアント認証あり）で以下を公開
  - Fulcrum（Electrum プロトコル、TLS）
  - Open WebUI（HTTP）
  - ダッシュボード（HTTP）
- クライアント側（Tails、Android）にクライアント認証鍵を配布する。
  これにより onion アドレスが漏れても第三者は接続できない

### 5.3 LAN 内

- 例外として、初期設定時のみモニター直結で作業する。SSH は onion 経由に限定するか、
  そもそも有効にしない（本機は直接操作できるため）

## 6. 役割分担（誰が・どこで・何をするか）

| 作業 | 場所 | 備考 |
|---|---|---|
| 残高確認・履歴閲覧 | Tails の Electrum → 自前 Fulcrum（onion） | 公開サーバーを使わなくなる |
| 送金（署名） | Tails | ADR-006 の分離運用を導入すれば署名専用 Tails |
| 外出先での確認 | Android → onion（ダッシュボード / Electrum Android） | 読み取りのみ |
| LLM との対話 | 本機直接、または Tails / Android → Open WebUI（onion） | 質問内容は外に出ない |
| 手元文書の投入（RAG） | 本機直接（USB 等で持ち込み）または Web UI からアップロード | 投入する文書の選別基準は要検討 |
| ノードの保守 | 本機直接 | コピペ手順書に従う |

## 7. 未決事項（ラウンド5以降）

- xpub を本機に置くか（置くと本機だけで残高ダッシュボードが作れるが、侵害時に全アドレスが割れる）
- LLM モデル取得の経路（Tor 限定か、clearnet 例外を認めるか）
- 価格など外部データの取得可否
- ダッシュボードの内容と重さ（mempool を入れるか、軽量自作で済ませるか）
- 物理環境（部屋への他人の出入り、ロック・暗号化方針）
- 運用時間の予算（週あたり）と、許容停止時間
